# v0.9.43 · 同一工作簿内多张表并行查询（多批次队列 + 按表暂存 + 批次分桶）

> 2026-10-29 · 触发：爹地问「现在貌似没有针对多表格同时查询的多线程能力？」——
> A 表点③之后切到 B 表再点，第二条被静默吃掉（`refresh()` 开头一句 `if (this.busy) return`）。

## 病根

- `busy` 是一个**面板级布尔值**：一轮查询期间，整块面板（同一工作簿的所有工作表）只允许跑一批。
  第二条不是失败，是**没有反应**——最糟的一种"没反应"。
- 一轮的状态（items / done / total / cfg / 错误 / 写回队列）全都挂在组件上，只有一份：
  想跑两批，先得让"一批"成为一等公民。
- 桥侧 `WPS_TRACK_CONCURRENCY`（默认 4）本来就有 `slot()` 排队，**瓶颈根本不在后端，在面板**。
- 跨工作簿天然并行（每个工作簿的 taskpane 是独立 webview），所以这一版只解决同一工作簿内多张表。

## 改法

### 1. 批次化：`busy` → `batches: Batch[]`

每点一次③开一批，`Batch` 自带快照，互不干扰：

```
{ id, seq, doc, sheet, cfg 快照, items, done, total, state, stop,
  errs: {action, write}, misalign/misalignSeen, writeStats/writeMs,
  colSnap/outSnap, capErr, summary, xsheet: {ok, fail} }
```

- 面板只留「当前在看哪一批」（`viewBatchId`）以及面板级错误 `panelErr`；
  `busy / items / done / total / writeStats / writeErr / misalign / capErr` 全部改成
  **按当前这一批读的 computed**——模板和横幅逻辑一行没改，读数来源从"全局"换成"这一批"。
- 同一张表默认不许再点（防手抖把同一段查两遍）；要并行就点新出现的**「再开一批」**。
- 不同表本来就不拦——这正是这次要的功能。

### 2. 切表检测（多表并行的前提）

`watchDocChange()`（900ms 轮询）发现活动表变了就按那张表重载列设置，并把视图切到那张表最近的一批。
以前只有面板启动时读一次配置，切表后用的还是上一张表的列——多表并行会直接把结果写进错的列。

**顺带修掉一个真 bug**：`refresh()` 原来在 `await this.ping()` 之后才取 `ActiveSheet` 快照，
桥慢/重连时用户已经切表 → 整批跑在错的表、错的单号列上。现在快照在任何 await 之前取。

### 3. 写回：按批次排队 + 按表写锁 + 按批次分桶

- **按批次写**：`writeQ` 的每条都带 `batchId`，落盘时按 `(batchId)` 归拢、按 `seq` 排序 → 先跑的批次先写。
- **按表写锁** `flushingDocs: Set`：同一张表同一时刻只允许一批在写。
- **后写覆盖前写（硬保证）**：`cellSeq: Map<doc|row|col, seq>` —— 一格如果已经被序号更大的批次写过，
  序号小的批次**不许再往回写**。否则"谁先 flush 谁赢"，结果取决于网络快慢，不是直觉。
- **`pendingWrites` 按批次分桶**：`key = batchId|doc|number|numCol|outCol|row`，
  同表点两次刷新时两批可能写同一行，必须能分开、按批次顺序补。

### 4. 跨表写：(a) 还是 (b)，让代码自己回答自己

未知：WPS et 的 JS API **能不能写非活动工作表**。

做法：不猜、不等实测——

| 现场 | 行为 | 计数 |
|---|---|---|
| (a) 能摸到非活动表 | 直接写进那张表，用户不用切回去 | `crossSheetWrite.ok` |
| (b) 摸不到（抛异常） | 自动回落到"攒着等切回"，切回来自动补齐 | `crossSheetWrite.fail` |

- 判据是**运行时**的：先对那张表做一次**只读** `Range('A1').Value2` 探针（不写不建不删），
  能读就试着写，写不进去的**逐条**转进待补队列（不算失败、不报错）。
- 启动时另有一次零风险自检：对活动工作簿的 `Sheets.Item(2)` 做只读取值，只记日志。
- 计数在**诊断日志**和 `window.__SHIPTRACK_CROSS__` 里都有；真机跑一轮多表后把两个数抄回来，
  就是 (a)/(b) 的实测答案。若是 (b)，代码已在保守路径上，不用改。

### 5. 并发上限（面板侧硬上限，不只靠桥排队）

- 同时最多 `MAX_BATCHES = 3` 批在跑（`window.__SHIPTRACK_MAX_BATCHES__` 可调），
  超出的批次进 `排队` 状态，空出一格立刻开跑（批次条上显示"排队"）。
- 全局在飞请求硬上限 `maxInflight = 4`（`window.__SHIPTRACK_MAX_INFLIGHT__` 可调）：
  每个 slot 背后是一个独立 Chrome profile，内存/CPU 是实的，不能靠桥在别处排队糊过去。

### 6. 失败隔离

`actionErr` / `writeErr` / `misalign` 全部拆到批次上：一批熔断（连续 3 次连接失败）只停它自己，
另一批照跑；横幅显示的是"你正在看的那一批"的状态。

### 7. UI：批次条

```
[ Sheet1 37/97 在跑 ] [ Sheet2 0/64 排队 ] [ Sheet3 97/97 完成 ]
```

点一下就切到那一批看明细（进度条、表格、横幅都跟着切）。
切到一张没跑过的表时表格是空的——绝不把别的表的行显示成这张表的。

## 顺带修掉的性能坑（自己踩的）

第一版用 `watch: { batches: { deep: true } }` 把批次摘要暴露给探针。Vue 的 deep 遍历会摸到批次里
`sheet`（WPS Worksheet 对象）的每个 getter —— `UsedRange` 一次就是一次**同步 COM**。
实测一轮多出 **219 次 COM**（184 → 404）。

两处修正：
- `sheet` 用 `markRaw()` 包起来，Worksheet 对象绝不进响应式代理；
- 摘要改成关键点显式 `publishBatches()`，不做 deep watch。

修完回到 **184 次 / 353ms**（与 0.9.42 的 184 次 / 359ms 持平，没有为了多表并行牺牲写回性能）。

`scripts/verify-all.sh` 11/11 全绿，状态机探针 **32/32**：

| H27 | (b) 现场（`__crossSheetBlock`）：跨表写计数 fail>0、结果不丢、切回自动补齐、残留待补=0 |

## 待真机验收（爹地）

1. 装 0.9.43 后，同一工作簿开两张表，各点一次③ → 两张表的进度条各自推进（切表看得到另一批还在跑）。
2. 打开「诊断 / 日志」，跑完后应出现两行 `第 N 批跨表写：成功 X / 回落 Y` —— 把 X/Y 抄回卡上，
   这就是"WPS 能不能写非活动表"的实测答案。
3. 一批跑着的时候切走再切回：结果要么已经写进原表（能跨表写），要么自动补齐（不能），
   两种情况都不该丢结果。
